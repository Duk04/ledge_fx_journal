# Languages (i18n)

The app speaks English and Mongolian (`en`, `mn`). Translation goes through
[next-intl](https://next-intl.dev) v4 **without i18n routing**: no `/mn/...`
URLs, and no locale logic in the middleware. Everything is behind sign-in, so
there is nothing to make crawlable per language, and a URL prefix would only
add a redirect to every link.

## Which language a request gets

`src/i18n/request.ts`, in this order:

1. **The `NEXT_LOCALE` cookie.** Signing in sets it from `User.locale`, and so
   does changing the language in Settings → Profile (`setLocale` in
   `lib/actions/locale.ts`).
2. **The browser's `Accept-Language`.** This decides the login page and a
   first visit. Registration stores the language the person registered in.
3. **English.**

`User.locale` is the durable copy, and the cookie is what a request reads. So a
choice made on one device follows the user to the next one at sign-in. The
`e2e/i18n.spec.ts` spec asserts exactly that.

`<html lang>` follows the locale.

## Where strings live

- `messages/en.json` and `messages/mn.json`, one namespace per area:
  - `nav`, `shell`, `palette`, `auth`, `dashboard`, `trades`, `journal`, `analytics`, `playbooks`, `simulate`, `calculator`, `accounts`, `backtest` and `settings`.
  - `enums` for labels shared across areas.
  - `ui` for the shared kit.
  - `errors` and `validation` for server text (see below).
- Keys are typed (`src/global.d.ts`), so a typo is a tsc error.
- `src/i18n/config.test.ts` fails if the two files ever have different keys or
  an empty message.

Which API to use:

- **Client components:** `useTranslations("ns")` at the top of each component.
- **Async server components and pages:** `await getTranslations("ns")`.
- **Non-async server components:** `useTranslations`.
- **Plain functions that build display text** (chart labels, `buildInsight`)
  take `t` as a parameter. Don't hand them pre-built English.

Plurals use ICU in English (`{count, plural, one {# trade} other {# trades}}`).
Mongolian has no plural forms (`{count} арилжаа`).

### English output is pinned

The English rendering stayed byte-for-byte what it was before translation,
because the Playwright specs select by exact English labels. That is why:

- **Counts are often passed as strings** (`String(n)`). ICU formats a bare
  number with grouping, so `1234` would render as `1,234`.
- **Some messages keep a literal `(s)`.**

Keep both habits when editing an existing message. A new message is free to
use real plurals.

## Server text: two paths

**Form-level errors (`formError`) are translated on the server.**

- An action calls `failT("tradeNotFound")` or `await tr("onlyLotsOpen", { lots })` from `src/i18n/server-t.ts`.
- That module resolves the language the same way `request.ts` does, and formats with next-intl's `createTranslator`.
- Outside a request (vitest, scripts) it falls back to English. That is why the DB tests still assert English sentences.
- It does not use `getTranslations` deliberately: that needs the plugin's request config, which vitest does not have.

**Validation messages travel as keys.**

- A zod schema is built once at module scope and shared by the browser (react-hook-form) and the action that re-validates. So it cannot know the reader's language.
- Schemas say `vmsg("entryRequired")` (`src/i18n/encoded.ts`), which encodes to a plain string `@v:entryRequired` (with JSON params after a `|` when there are any).
- `FieldError` translates it in the browser. It is the one place every field error passes through.
- `failZod()` / `localizedFieldErrors()` translate it on the server, for call sites that show a field error somewhere other than a `FieldError` (a toast, a banner).
- A message without the prefix passes through untouched, so anything missed degrades to English, never to a raw key.
- In tests, `english()` (`src/i18n/english.ts`) renders an encoded message so assertions read the sentence.

**Risk-guard breaches** (`lib/risk.ts`) carry both shapes:

- An English `message`, for logs and tests.
- A `key` + `values` pair, which `RiskGuard` renders from `dashboard.risk.*`.

**Analytics row labels** (session, weekday, plan, direction) come out of the queries in English. `BreakdownTable labelNs` and the session heatmap translate them by the row's key instead.

## Deliberately not translated

- **Numbers, money, percentages and dates.** `lib/metrics/formatters.ts` formats them in the trading convention (`$1,234.56`, 24-hour time, `Aug 17`) in either language. Month names in date patterns are therefore English. Localising them means threading the locale into `formatInZone`, which is a follow-up rather than an accident.
- **Statement and candle parser warnings** (`lib/statements`, `lib/candles/parse.ts`). They run in the browser for the preview as well, and quote the file's own column names.
- **Worker and sandbox errors from strategy code.**
- **Enum codes shown as codes:** `LONG`/`SHORT` badges, `LIVE`/`MT5`, `OPEN`/`CLOSED` on the journal.
- **`global-error.tsx`.** It renders its own `<html>` outside the provider.
- **Product and trading terms:** "Profit factor", "Expectancy", "stop loss", "take profit", "Playbook", and symbol and currency codes.

## Adding a language

1. Add the code to `LOCALES` and a label to `LOCALE_LABELS` (`src/i18n/config.ts`).
2. Add `messages/<code>.json` with every key. The parity test lists the missing ones.
3. Add it to `MESSAGES` in `src/i18n/server-t.ts`.
