# PWA

Ledger installs as a standalone app on desktop and mobile. This document
covers the caching strategy, the one deliberate scope cut (no offline write
queue), and install instructions.

## Files

| File | Role |
|---|---|
| `public/manifest.webmanifest` | Name, icons, `display: "standalone"`, the "Log trade" shortcut |
| `public/icons/*` | App icons — see "Icons" below |
| `public/sw.js` | The service worker |
| `src/components/pwa/register-sw.tsx` | Registers `sw.js` on mount |
| `src/components/pwa/offline-banner.tsx` | The "you're offline" strip |
| `src/components/pwa/use-online-status.ts` | The `navigator.onLine` hook both of the above (and any write-form) can share |

`register-sw.tsx` and `offline-banner.tsx` are both mounted once, in
`src/app/(app)/layout.tsx`. `<html>`/`<head>` (`src/app/layout.tsx`) already
points at the manifest and declares `appleWebApp: { capable: true }` — that
part needed no changes here.

## Caching strategy

The worker (`public/sw.js`) draws one hard line, and everything else follows
from it:

> **A journal must never show a stale P&L number.**

- **HTML navigations and every `/api/*` request → network-first.** Always
  try the network; only fall back to a cached copy if the network genuinely
  fails (offline, DNS down). A slightly-stale dashboard shown *because the
  network is unreachable* is an acceptable degradation; a stale dashboard
  shown *because the worker preferred its cache* is not — that's the
  difference between these being network-first and cache-first.
- **Hashed static assets (`/_next/static/*`, `/icons/*`) → cache-first.**
  Their filename encodes their content hash, so "stale" isn't a real
  possibility for these — a new build ships new filenames, and the old,
  cached ones can be served instantly forever.
- **Everything else** passes through with no opinion (normal HTTP caching
  applies).

On activate, the worker deletes any cache whose name doesn't match the
current `SW_VERSION` and calls `self.skipWaiting()` / `clients.claim()`
during install/activate — a new deploy takes over on the very next
navigation, no "reload to update" prompt needed. That's safe specifically
*because* there's no offline write queue to worry about stranding (see
below): an abrupt takeover can't lose a mutation the old worker didn't know
about.

The worker never intercepts a non-`GET` request — writes always go straight
to the network and get to fail (or succeed) on their own terms.

## Why there is no offline write queue

The obvious next step for a journaling app would be: let the trade form
submit while offline, queue the write, replay it when the connection comes
back. This is explicitly **not implemented**, and that's a scope decision,
not an oversight:

- **Ordering and conflicts are real problems here, not edge cases.** A
  queued "close trade" that replays after a queued "delete trade" (or after
  someone edited the same trade from another device in the meantime) needs a
  conflict-resolution story. Getting that wrong is worse than not having the
  feature.
- **A half-working queue's failure mode is silently losing a trade.** That
  is the one failure mode this app cannot have — a missing feature is an
  inconvenience; a trade that the user believes was logged but wasn't is a
  broken product.
- **The honest alternative is cheap and reliable:** tell the user plainly
  that they're offline, and disable the write instead of pretending to
  accept it.

That alternative is the whole implementation:

- `<OfflineBanner>` renders a warn-toned strip — "You're offline — changes
  won't save until you're back online." — the moment `navigator.onLine`
  (via `useOnlineStatus()`) goes false, and disappears the instant it comes
  back.
- Any write surface should disable its own submit under the same condition.
  The trade form (`src/components/trades/trade-form.tsx`, owned outside this
  change) should import `useOnlineStatus()` from
  `src/components/pwa/use-online-status.ts` and disable its submit button
  while offline, with `title`/helper text pointing at the banner's
  explanation. `src/components/trades/attachment-uploader.tsx` already does
  this for screenshot uploads.

If a real offline queue is ever built, it should be a deliberate, separately
reviewed feature with its own conflict story — not something bolted onto the
service worker as an afterthought.

## Icons

Generated by `scripts/make-icons.mjs` from the same two-candle glyph used as
the wordmark in `src/components/shell/app-shell.tsx` (drawn fresh, not a
screenshot). Run `node scripts/make-icons.mjs` to regenerate after changing
the glyph or the brand colours; it writes:

- `icon.svg`, `icon-maskable.svg` — vector sources
- `icon-192.png`, `icon-512.png` — standard icons, transparent background
- `icon-192-maskable.png`, `icon-512-maskable.png` — full-bleed background
  with the glyph inset to the safe zone, for Android's adaptive-icon masking
- `apple-touch-icon.png` (180×180, opaque background — iOS composites
  transparency as black)

The script rasterises with `sharp` — already present in `node_modules` as an
optional dependency of `next` itself (used for `next/image`), so nothing was
added to `package.json` to get it — and falls back to a small hand-rolled
PNG encoder (raw RGBA buffers + Node's built-in `zlib.deflateSync`, still no
new dependency) if `sharp` can't be loaded, drawing the same glyph as filled
rectangles. Either path produces the real brand mark; neither ships a
placeholder grey square.

**`apple-touch-icon.png` is not currently linked from `<head>`.** iOS looks
for a `<link rel="apple-touch-icon">` tag (`src/app/layout.tsx`), which is
outside this change's file list. Whoever owns that file should add:

```html
<link rel="apple-touch-icon" href="/icons/apple-touch-icon.png" />
```

Until then, Android/desktop install (which reads the manifest's `icons`
array directly) gets the full icon set; iOS home-screen installs will use a
generic screenshot-based icon instead of the candle mark.

## Installing

**Android (Chrome):** visit the app, then either tap the "Install app"
banner Chrome shows automatically, or open the browser menu (⋮) →
**"Install app"**. It installs using the manifest's icons and opens in
`standalone` display (no browser chrome), with "Log trade" available as a
long-press shortcut on the home-screen icon.

**iOS (Safari):** open the app in Safari, tap the **Share** icon, then
**"Add to Home Screen"**. `appleWebApp: { capable: true }` in
`src/app/layout.tsx` is what makes the installed icon open full-screen
(`standalone`-equivalent) instead of inside Safari's chrome. (See the
apple-touch-icon note above for the one rough edge on iOS today.)

**Desktop (Chrome/Edge):** an install icon appears in the address bar; click
it, or use the browser menu's "Install Ledger…" entry.
